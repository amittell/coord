## Themes

1. The Postgres/HA path is not production-ready yet. Three db.py methods bypass the backend seam and open raw SQLite, which on Postgres breaks the v0.42 repo-scope guards (500s on a fresh deploy, silent cross-repo bypass with a stale SQLite file). Postgres has no migration path (bootstrap stamps schema 18 while MIGRATIONS is at 19). The HA-cutover manifests cannot work as shipped: the pinned image lacks asyncpg, postgres.yaml bundles a stub Secret that clobbers real credentials, and the runbook selects pods by a label no pod carries and execs a sqlite3 CLI the image does not ship. Process-local locks (queue admission quota) and the never-released ~3h leader lease are single-process assumptions that break multi-replica or rolling-deploy behavior.

2. Queue lifecycle has systematic gaps. The FIFO queue is drained only on explicit release_claims; release_session, respond_to_request(approved/narrowed), and TTL/idle expiry strand waiters. A no-op release still drains the queue for an active claim. mark_queue_expired/granted lack state guards, so a waiter timeout racing a drain creates an orphan claim the requester was told 409 about. The queue-row reaper exists but has zero callers. A client disconnect during the long-poll orphans the waiting row. Multi-item claims with wait_seconds report clean success while only one item was actually claimed.

3. The v0.44/v0.45 write-scaling work has lock-holding and coverage gaps. LSP documentSymbol roundtrips run inside the claim-grant transaction while holding the global writer lock and the SQLite write lock. Database.init() is not memoized on SQLite, so every operation takes a BEGIN IMMEDIATE migration check. touch_engineer_token writes per authenticated request outside the writer funnel. Disabling the writer queue reopens a double-grant TOCTOU. The writer queue itself has no direct failure-path tests.

4. Identity is authenticated but not bound to actions. Mutating endpoints accept an arbitrary or omitted engineer regardless of the token used; respond_to_request never authorizes the caller as the holder; my_requests(queued=True) filters by env-derived requester rather than the engineer used at claim time, hiding queue rows.

5. CLI env-file handling is inconsistent and can destroy credentials. coord init re-run and coord upgrade can both clobber COORD_AUTH_TOKEN; upgrade's rewrite drops other COORD_* keys and comments; CLI token precedence is the opposite of the MCP wrapper and the docs; doctor can crash mid-diagnosis; a failed background start leaks an orphan server process.

6. Docs and templates drift behind the code. README pins v0.28.2 on a v0.45.0 repo; the shipped pre-push hook template is the legacy fail-open version; MCP templates ship unrecognized placeholders; getting-started documents an extend-claims workflow that has no tool or command.

## Confirmed findings (57)

### HIGH | coordination/db.py:3141 | claim_repo/request_repo/queue_entry_repo bypass the backend seam and open raw SQLite, breaking repo-scope guards on the Postgres backend

Category: sqlite-vs-postgres-divergence. Found by r1:db; adversarially verified.

These three methods are the only ones that connect with `async with aiosqlite.connect(self.path) as conn:` (lines 3141, 3153, 3167) instead of the overridable `self._connect()` seam every other method uses. PostgresStore inherits them unchanged (no override exists in pg_backend.py; grep confirms) and PostgresStore.__init__ calls `super().__init__(path)`, so `self.path` is the SQLite path. main.py's scope guards call them on every id-addressed operation from a repo-scoped token (`exists, repo = await get_service().db.claim_repo(claim_id)` at main.py:832, plus :841 and :850). On a Postgres deployment: a fresh environment gets an empty SQLite file created as a side effect and `SELECT repo FROM claims` raises OperationalError 'no such table: claims' -> 500 on every scoped release/extend/respond/cancel; if a stale SQLite file from a prior SQLite run exists, the guard consults stale data -- a missing row returns `(False, None)` and the guard falls through, silently disabling cross-repo isolation for id-addressed operations.

Fix: Route the three methods through `self._connect()` (they need only row_factory + a single SELECT, exactly like get_queue_entry), or override them in PostgresStore. Add a PG-backend test that exercises _require_claim_in_scope.

### HIGH | coordination/main.py:125 | Leader lease is never released on shutdown and the TTL is ~3h, so every rolling deploy stalls all background work cluster-wide

Category: failover-stall. Found by r4:HA leader-lease + background-loop failover correctness; adversarially verified.

leader_lease_ttl = max(settings.cleanup_interval_sec, settings.auto_demote_interval_sec, settings.webhook_delivery_interval_sec) * 3 + 5. With defaults (cleanup=900, auto_demote=3600, webhook=5) this is 3600*3+5 = 10805s (~3 hours). The TTL multiplies the SLOWEST interval even though the live leader renews as fast as the FASTEST loop (webhook loop re-acquires every 5s), so the safety margin is enormous. Compounding this, the shutdown path never releases the lease: the finally block (lines 227-242) only cancels the loop tasks, calls db.aclose(), and shuts down the LSP pool -- there is no release_leader_lease() call, and no such method exists on either backend (the only write to coord_leader_lease is the acquire UPDATE at pg_backend.py:933). On a rolling deploy the drained leader pod exits leaving its coord_leader_lease row with holder_id set and expires_at ~3h in the future; every other replica's acquire_leader_lease hits `row['holder_id'] != holder_id and row['expires_at'] > now` and returns False. Result: claim expiry, auto-demote, AND webhook/PR-comment delivery all pause for up to ~3 hours after every deploy (and identically after any SIGKILL/OOM crash, where graceful release could not help anyway). For a system whose core purpose is TTL-based claim expiry, a 3h failover gap on a routine operation is a serious operational defect.

Fix: Add a release_leader_lease(lease_name, holder_id) that DELETEs (or clears) the row only when holder_id matches, and call it in the lifespan finally block. Independently, size the TTL off the RENEWAL cadence (min interval) rather than the max, e.g. a small fixed multiple of min(intervals) with a sane floor/ceiling, so a crashed leader fails over in seconds-to-minutes instead of hours. On SQLite acquire returns True unconditionally so both changes are Postgres-only no-ops.

### HIGH | coordination/main.py:223 | GitHub PR-comment delivery is dead unless COORD_WEBHOOK_URL is also set

Category: silent-failure. Found by r4:Webhook/GitHub outbox delivery semantics (no slice owned it); adversarially verified.

The background delivery loop is the only thing that drains the outbox, and it is only started when a plain webhook URL is configured: `if settings.webhook_url:  tasks.append(asyncio.create_task(webhook_delivery_loop()))` (main.py:223-224). But `fire_webhook` enqueues `kind='github'` rows gated solely on the token -- `if kind == "github":  if not (self.settings.github_token or "").strip():  return None  url = (self.settings.webhook_url or "").strip() or "github://pr-comment"` (service.py:3059-3062) -- so a github row is written even with `webhook_url` empty. config.py:118-120 documents github as an independent alternative ("instead of POSTing to webhook_url ... mirroring how webhook_url gates webhooks"), so `COORD_GITHUB_TOKEN` set with `COORD_WEBHOOK_URL` unset is a documented-valid config. In that config the loop never starts: every `push_bounced` bounce comment silently never posts, and the github rows sit `status='pending'` forever, growing the outbox unbounded with no exhaustion (they are never even attempted).

Fix: Start webhook_delivery_loop when either webhook_url or github_token is configured, e.g. `if settings.webhook_url or settings.github_token:`.

### HIGH | coordination/mcp_server.py:1014 | my_requests(queued=True) filters by env-derived requester, not the engineer used in claim_files, so queue rows are invisible

Category: bug. Found by r1:mcp-client; adversarially verified.

my_requests builds `requester = os.environ.get("COORD_REQUESTER", "").strip() or os.environ.get("COORD_USER", "").strip() or "agent"` and always sends it as the `requester` query param. Server side, GET /requests?queued=true filters strictly: `rows = await get_service().db.list_queued_with_holder(engineer=requester, ...)` (main.py:2430), and queue rows are created with `requester_engineer=body.engineer` from the claim_files POST body (service.py:2789). claim_files takes `engineer` as an explicit per-call argument, but my_requests exposes no engineer parameter at all. Whenever the engineer name passed to claim_files differs from COORD_USER/COORD_REQUESTER (or those are unset, defaulting to "agent"), my_requests(queued=True) silently returns an empty list even while the caller has live queue entries. CLAUDE.md explicitly advertises "Inspect your own queue rows via my_requests(queued=True)", so agents will conclude they are not queued and re-claim or give up.

Fix: Add an optional `engineer` parameter to my_requests (mirroring claim_files/release_claims) and use it as the `requester` param when provided; fall back to the env chain only when absent. Alternatively have the server match queued rows by session_id (already sent on claim_files) in addition to requester_engineer.

### HIGH | coordination/overlap_symbols.py:308 | Same symbol on same file granted to two agents when the file path is spelled differently

Category: false-negative-overlap. Found by r1:symbols; adversarially verified.

In _classify_symbol_symbol, holder symbols are keyed on the verbatim stored file_path ('f = str(row["file_path"])') and requester symbols on the verbatim request pattern (service.py:1051 builds '{item.pattern: list(item.symbols)}'; service.py:1596 stores 'item.pattern' as claim_symbols.file_path). But the path-overlap gate that routes into this branch uses engine._normalize_pattern, which strips a leading './', a leading '/', and converts backslashes. So holder pattern './src/auth.py' [login] vs requester 'src/auth.py' [login] passes heuristic_overlap (both normalize to 'src/auth.py', overlapping_paths == ('<unknown>',)), then candidate_files = {'./src/auth.py', 'src/auth.py'}; for each file one of held_paths/req_paths is empty, so no pair matches and the result is AUTO_COEXIST -- both agents hold a live claim on the identical symbol of the identical file with no 409, no queue, no warning. The same happens for 'src\\auth.py' (Windows client) vs 'src/auth.py' and '/src/auth.py' vs 'src/auth.py'. This is exactly the worst case the sub-file-claims design is meant to prevent, and nothing at claim intake canonicalizes item.pattern before storage or comparison.

Fix: Normalize file keys with engine._normalize_pattern on both sides inside _classify_symbol_symbol (holder_by_file and requester_by_file key construction), and preferably also canonicalize item.pattern once at claim intake before it is stored into claim_symbols.file_path, so stored rows, conflict responses, and the rename sweep all agree on one spelling.

### HIGH | coordination/service.py:2660 | A no-op release (wrong engineer / unauthorized) still drains and flushes the entire queue for an active claim

Category: correctness. Found by r1:service; adversarially verified.

The comment at lines 2660-2662 claims: "_drain_queue_for is idempotent -- if the id wasn't really released (wrong engineer, already gone), pop_next_waiting returns None and the call is a no-op." That is false: `db.pop_next_waiting_queue_entry` (db.py:2008) selects `FROM claim_queue WHERE blocking_claim_id = ? AND state = 'waiting'` with no check that the blocking claim was actually released. `service.release_claims` drains for every input cid regardless of whether `db.release_claims` matched (`WHERE id = ? AND engineer = ?` can update 0 rows). So `POST /claims/release` with a claim id and a mismatched engineer name releases nothing, but `_drain_queue_for` then pops the head waiter, re-runs create_claims, re-conflicts with the still-active holder, marks the entry expired, notifies the waiter with no grant -- and the `while True` loop repeats for the NEXT waiter until the queue is empty. One failed release call expels every queued waiter on that claim with an immediate 409, destroying their queue positions and the wait_seconds they asked for.

Fix: Only drain claim ids that were actually released: have `db.release_claims` return the released id list (it already builds `released_ids` internally) and drain only those. Additionally, make `pop_next_waiting_queue_entry` (or `_drain_queue_for`) verify the blocking claim has `released_at IS NOT NULL` before popping, and on re-conflict with the SAME still-active holder, re-queue the entry (state back to 'waiting') instead of expiring it.

### HIGH | coordination/service.py:2663 | FIFO queue is only drained on explicit release_claims; release_session, respond_to_request(approved/narrowed), and TTL/idle expiry strand queued waiters

Category: queue-liveness. Found by r1:service; adversarially verified.

The only caller of `_drain_queue_for` is `release_claims` (`for cid in claim_ids: await self._drain_queue_for(cid)`, line 2663-2664). Every other path that closes a claim never drains its queue: (1) `POST /sessions/{id}/release` calls `db.release_for_session` directly (main.py:2276), bypassing the service drain entirely -- and release_session is the protocol-recommended end-of-session cleanup; (2) `respond_to_request(decision='approved'|'narrowed')` releases the holder's claim inside `db.respond_to_request` (db.py:3903+) with no drain; (3) TTL/idle expiry via `db.expire_stale_claims` (called from the cleanup loop in main.py:152 and from service entry points) closes claims and cascade-resolves *requests* but never touches `claim_queue`. This last one is especially wrong because `file_request` exists to *shorten the holder's TTL* so it expires sooner -- yet when that shortened TTL fires, waiters queued with `wait_seconds` behind that claim get nothing. The waiter's hybrid loop in `_enqueue_and_wait` only polls its own queue-row state (which stays 'waiting'), so it burns the full wait_seconds and then surfaces a 409 even though the scope has been free the whole time. Docs promise 'on release the next queued requester is auto-granted'.

Fix: Route all claim-closing paths through a shared drain: have release_session and respond_to_request (approved/narrowed) call `_drain_queue_for` for each released claim id, and have the service/cleanup-loop expiry path collect the ids `expire_stale_claims` closed (it already returns/knows `actually_closed`) and drain each. Alternatively, add a fallback check in `_enqueue_and_wait`'s poll iteration: if the blocking claim is no longer active, attempt a self-grant.

### HIGH | coordination/service.py:2864 | Multi-item claim batch with wait_seconds returns a clean success covering only one item; the rest are silently unclaimed

Category: silent-failure. Found by r1:service; adversarially verified.

When any item in a batch conflicts, nothing is inserted (`if not conflicts:` gates the whole insert). `_enqueue_and_wait` then enqueues ONLY the first conflicting item (line 2749 `target_item = body.claims[0]` / pattern match) and on a drain grant returns `CreateClaimsResponse(claim_ids=[granted_cid], conflicts=[], warnings=[], options=[])` (lines 2864-2870). For a request with N>1 items -- including items that never conflicted at all -- the caller receives a success-shaped response with empty conflicts and empty warnings, and N-1 files remain completely unclaimed. `create_refactor_claims` explicitly patches this exact hole for its machine-generated batches ('refactor reservation is PARTIAL...'), but a hand-built multi-file `claim_files(..., wait_seconds=60)` gets no such warning, so an agent will edit files it never reserved.

Fix: Mirror the refactor guard in the plain path: when `_enqueue_and_wait` returns a grant and `len(body.claims) > 1`, append a warning naming the patterns that were NOT reserved (everything except the granted item), or better, re-attempt `create_claims` for the remaining items after the grant and merge results.

### HIGH | deploy/k8s/ha-cutover/deployment.yaml:42 | HA-cutover manifest pins a release image that cannot speak Postgres (no asyncpg in the image)

Category: ha-cutover-sanity. Found by r1:ops; adversarially verified.

The cutover Deployment sets `COORD_DATABASE_URL` (secretKeyRef coord-pg) against `image: ghcr.io/amittell/coord:v0.45.0@sha256:a55e767f...` -- the standard release image. That image is built by Dockerfile via `pip install -r /build/requirements.txt -r /build/requirements-otel.txt` then `pip install --no-deps .`; neither requirements file contains asyncpg (it lives only in pyproject's optional `postgres = ["asyncpg>=0.30.0"]` extra). coordination/pg_backend.py guards the import (`except ModuleNotFoundError: asyncpg = None`, lines 46-52) and has no `asyncpg is None` check anywhere, so `PostgresStore.init()` -> `_get_pool()` -> `_POOL = await asyncpg.create_pool(dsn, ...)` raises AttributeError on NoneType at startup. All 3 replicas would CrashLoop on cutover day -- the exact 2026-07-05 incident the runbook header warns about ("an image that could not speak Postgres"). The manifest's own repin instruction ("copy the image line from deploy/k8s/prod/deployment.yaml") repins to another asyncpg-less image, and tests/test_deploy_overlay.py does not cover deploy/k8s/ha-cutover/.

Fix: Add pinned asyncpg to the container image (append to requirements.txt or add a requirements-postgres.txt installed in the Dockerfile), add a fail-fast guard in pg_backend (raise RuntimeError('COORD_DATABASE_URL is set but asyncpg is not installed; install coord-mcp-server[postgres]') when asyncpg is None), and add a CI/docker-smoke assertion that the built image can `python -c "import asyncpg"`.

### MEDIUM | coordination/cli_doctor.py:210 | coord doctor crashes with UnboundLocalError when the /claims probe raises after /readyz succeeded

Category: crash. Found by r1:cli; adversarially verified.

In _check_service the except branch references `hint` which is only assigned inside the try block AFTER the /claims response returns: `except httpx.HTTPError as exc: out.append(CheckResult(label, False, str(exc), hint,))`. ### MEDIUM | coordination/cli_init.py:291 | Re-running coord init unconditionally clobbers the real token in .coordination/local.env with no guard

Category: destructive-operation. Found by r1:cli; adversarially verified.

`_write_local_env` always rewrites local.env: in remote mode `token = os.environ.get("COORD_AUTH_TOKEN", "set-me")`, in local mode it takes the ~/.coord/token file. Re-init is an explicitly supported flow (cli_upgrade.py comment: "running init twice with different --tool values is supported and additive"), and the documented v0.42 workflow tells operators to paste repo-scoped tokens into local.env. So `coord init --tool codex` in an already-wired remote-mode repo, run without COORD_AUTH_TOKEN exported, silently replaces the working scoped token with the literal `set-me`; in local mode it replaces an operator-minted scoped token with the shared ~/.coord/token. Unlike owners.yaml (guarded by `if not owners_path.exists() or args.force`) and unlike coord upgrade (which at least tries to preserve the token), local.env has no exists-check, no --force gate, and no preservation.

Fix: Mirror the upgrade path: read the existing local.env via read_env_file and preserve a non-placeholder COORD_AUTH_TOKEN (and other keys) unless --force is passed; only mint/backfill when the existing token is absent or a placeholder.

### MEDIUM | coordination/cli_ops.py:306 | CLI token precedence (local.env beats exported env) is the opposite of the MCP wrapper and the documented behavior

Category: doc-vs-code-drift. Found by r1:cli; adversarially verified.

`_resolve_service` resolves `token = repo_env.get("COORD_AUTH_TOKEN") or os.environ.get("COORD_AUTH_TOKEN", "")` -- local.env wins over a real exported env var. The MCP wrapper does the reverse: mcp_server._load_local_env sets env keys "only if the variable is currently unset or holds a known placeholder" ("Explicit env ... wins; placeholders lose"), and commit 752ecd8 documents exactly that ("real env tokens shadow repo-scoped local.env tokens"). So in a shell with COORD_AUTH_TOKEN exported, `coord status` / `coord claims` / `coord release` authenticate with the local.env token while coord-mcp (and its coord_notice scoping warnings) authenticates with the exported one -- an operator can see `coord status` pass while the agent 401s, or debug the wrong token's repo scope.

Fix: Align precedence with the MCP wrapper (real env wins, placeholder values lose) or explicitly document the CLI's deliberate divergence; also treat the 'set-me' placeholder as unset here as _clean_repo_id already does for repo ids.

### MEDIUM | coordination/cli_start.py:176 | Failed background start leaks an orphan server process and deletes a PID file that was never written by this run

Category: resource-leak. Found by r1:cli; adversarially verified.

In run_start's failure path (`except RuntimeError as exc:`), the code prints the error, unlinks `~/.coord/coord.pid` if it exists, and returns 1 -- but never calls `proc.terminate()`/`proc.kill()`. On a readiness timeout (cold start slower than the 15s default) the spawned `coordination.cli _serve` process keeps running: it can bind the port and the SQLite DB seconds later, yet no PID file records it, so `coord stop` reports "No background coord service recorded" and cannot stop it. Additionally, `_write_pid_file` only runs AFTER readiness succeeds, so any coord.pid present at failure time necessarily belongs to a DIFFERENT, possibly still-healthy background service (e.g. one started on another port) -- unlinking it orphans that service's stop record too.

Fix: On the failure path, terminate the freshly spawned process (proc.terminate(); proc.wait(timeout=...); escalate to kill) and do not unlink a PID file this invocation never wrote.

### MEDIUM | coordination/cli_tokens.py:331 | coord tokens list truncates token ids to 8 chars but rotate/revoke require the full uuid

Category: bug. Found by r1:auth-config; adversarially verified.

_list renders `tid = r["id"][:8]` under the TOKEN ID column, while token ids are full uuid4 strings (db.create_engineer_token: `token_id = str(uuid4())`) and both rotate_engineer_token and revoke_engineer_token match with `WHERE id = ?` (exact).
